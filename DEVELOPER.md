## Git
Правила оформления коммитов, веток и Pull Request (PR).

### Commit
Коммит должен содержать ёмкое сообщение с описанием конкретных изменений. Один коммит - изменения в конкретном блоке кода; нельзя смешивать правки логики, рефакторинг и новые фичи. На каждое логически завершённое изменение - отдельный коммит (кроме мусорных правок вроде комментариев и т. д.).

Сообщение должно быть написано в формате:
```zsh
git commit -m "edit (devClass.java): delete object duplication during comparison"
# Примеры глаголов основного действия: add, edit, delete, fix
```
Также в скобках можно указывать номер issue, чтобы привязать коммит к задаче из таблицы.

### Branch
Для каждой отдельной фичи должна создаваться отдельная ветка с чётким и понятным названием:
```zsh
git switch -c vladislav/bug-fixes-auth
```
Флаг `-c` позволяет создать и сразу переключиться на ветку. 

В отличие от коммита, ветка создаётся под объёмный блок изменений. Создавать её нужно от главной ветки разработки - `develop`. По настроенным правилам (`branch rules`) на GitHub после слияния (merge) личная ветка автоматически удаляется с удалённого сервера.

**Основные постоянные ветки:**
* `main` - основная ветка, которая хранит готовый к использованию (релизный) код. Вливать сюда код напрямую из личных веток запрещено — изменения попадают в `main` только через [Pull Request](#pull-request) из ветки `develop`.
* `develop` - ветка, в которой идёт процесс разработки. Весь код из личных веток вливается именно сюда.

### Pull Request
Ветка `develop` принимает в себя изменения из индивидуальных веток. Далее код вливается в `main` осмысленными частями - например, после создания первой версии (MVP) или добавления крупных фич. Перед слиянием код должен исправно работать, а все тесты — проходить.

Сам PR на GitHub должен содержать чёткое название в формате:
```text
develop -> main | Краткое описание проделанной работы
# Вместо develop может быть имя вашей локальной ветки
```
В описании Pull Request должен быть ёмкий комментарий с обзором всей проделанной работы.

**Правила ревью:**
* **Личная ветка $\rightarrow$ `develop`:** должен быть назначен как минимум один проверяющий. Слияние разрешено только после одного апрува (желательно реально смотреть, что там написано).
* **`develop` $\rightarrow$ `main`:** для слияния требуется не меньше 3 апрувов от любых участников проекта.

### Базовый сценарий работы
```zsh
git switch develop                     # Переключение на основную ветку разработки
git pull origin develop                # Получение актуальных изменений

git switch -c vladislav/auth-IS345     # Создание локальной ветки и переход в неё
git push origin vladislav/auth-IS345   # Отправка локальной ветки на удалённый сервер

# ...код

git add README.md DEVELOPER.md         # Добавление файлов в индекс
git commit -m "add (documentation): add README and edit DEVELOPER" # Фиксация изменений
git push origin vladislav/auth-IS345   # Отправка коммитов на удалённый сервер

# ...далее: новые фичи, создание PR или завершение работы
```

## Code Style
* Единообразие: используйте одинаковые отступы (пробелы или табуляции) и расстановку скобок по всему проекту.
* Комментарии: старайтесь оставлять осмысленные комментарии к функциям/классам. Обязательно для тяжелой бизнес логики.
* Длина строк и воздух: ограничивайте длину строки (80–120 символов) и разделяйте логические блоки пустыми строками.
* Понятные имена: давайте переменным, функциям и классам осмысленные названия в принятом для языка регистре (camelCase). Избегайте непонятных сокращений и «магических чисел».
* Простота и структура: уменьшайте вложенность условий (например, через ранний return), не дублируйте код и пишите комментарии только там, где важно объяснить почему решение устроено именно так, а не что делает очевидная строка.
